# mini-world-model：微型世界模型 × 语言模型融合的具身 Agent

一个 **CPU 几分钟就能训完** 的最小世界模型（world model），用来搞懂"世界模型"四个字到底是什么意思。
纯 PyTorch + numpy 实现，无 gym / box2d / CUDA 依赖。

现已演进为完整系统：**世界模型 + 语言模型 + 常识库 + 符号计算器 + MPC/PD 导航**，
统一为 `MiniWorldAgent` 单入口（`agent.py`），支持 CLI / HTTP API / MCP Server 三种调用方式。

## 快速验证

```bash
pip install -r requirements.txt
python agent.py --state                # 环境状态
python agent.py "你看到了什么？"         # 感知（潜状态注入语言模型）
python agent.py "光速是多少？"           # 常识（669 条检索）
python agent.py "去目标那儿"             # 任务（MPC 规划 + PD 控制导航）
python agent.py "23 乘以 7"              # 符号计算器
```

## 版本控制

本仓库只跟踪代码与文档（约 300K）。权重（`*.pt`）、语料（`*.txt`）、
配对数据（`*.jsonl`）都是训练产物，不进 git —— 全部可按流程重训生成，
仓库保持轻量、diff 只反映代码变化：

```bash
python train.py                        # 世界模型（CPU 4 分钟）
python train_lm_state.py --epochs 4    # L2 具身语言模型（GPU 约 12 分钟）
```

单独部署时把生产权重放在仓库根目录即可（`agent.py` 默认找
`checkpoint.pt` + `lm_state.pt`）。

## 三域融合：lm_unified（对话 + 知识 + 世界叙述）

语言模型的能力分裂成两块——lm_state 会感知不会聊天，lm_dialog 会聊天不会知识。
融合的解法是训一个"文本域全能"模型：**把三个领域的语料合在一起训**。

`corpus_mixed.py` 合并三源生成 1430 条 QA（5.9 万字符）：
1. **对话域**：385 条手写对话（身份/能力/礼貌/场景问答）
2. **知识域**：669 条常识库自动转 QA（8 种问法模板轮换，避免全库一个问法）
3. **世界叙述域**：位置/方向/动作/导航机制的自然语言表达（教它把世界"讲出来"）

从 lm_dialog 续训 8 epochs（loss 1.68→0.58），得到 `lm_unified.pt`。

### 最终分工：两模型优势互补

```
世界模型 ──encode──> 32 维潜状态 ──注入[STATE]──> lm_state ──> 感知描述
    │                                                       （方位精确）
    ├──imagine──> MPC 规划 ──> 真实动作 ──> 环境推进
    │
lm_unified（对话+知识+世界叙述）──组织语言──> 四层兜底回答
常识库 669 条 ──精确检索──> ┘
```

| 通道 | 负责 | 实测 |
|---|---|---|
| `lm_state.pt` | 真·视觉感知（潜状态注入） | 画面描述/方位判断 |
| `lm_unified.pt` | 对话 + 知识 + 世界叙述 | 11 项交流零幻觉 |
| 常识库 | 精确知识 | 长城/光速/秦始皇全对 |
| 世界模型 | 导航 + 想象 + 规划 | 6/8 成功率 |

**关键设计：感知通道隔离历史上下文**。多轮上下文对对话有用，但会挤掉
`[STATE]` 的位置，导致 state 注入失效、感知回答退化成百科幻觉
（实测：先问 4 个知识问题再问"你看到了什么"，答成美国奇幻电影）。
修法：`_generate(..., use_ctx=False)`——感知是不依赖对话历史的独立通道。

## 两个参考项目的对照与融合

### [MiniMind](https://github.com/jingyaogong/minimind) → 语言模型侧

已落地：Pretrain → SFT 两阶段、loss mask（只学 assistant）、
conversations 多轮格式、Tool Call 数据、cosine+warmup、梯度裁剪、
优化器状态存档、BPE 6400 词表（压缩率 1.82）。

### [LingBot-World](https://github.com/robbyant/robbyant/lingbot-world) → 世界模型侧

它是**视频生成型**世界模型（基于 Wan2.2 视频 DiT，14B 参数，480P/720P），
和我们的像素级动力学模型尺度差 5 个数量级（167 万参数），**无法直接搬用**。
但有三个思想可以借鉴：

| LingBot-World | 我们的对应 | 今晚的落地 |
|---|---|---|
| **Action-conditioned 控制**（act2cam：动作字符串 → 相机运动） | 2 维加速度 | MPC 候选从 8 个固定方向 → **连续采样 + 瞄准方向邻域**（`_mpc_candidates`） |
| **Fast 版分块增量推理**（KV cache 逐块） | 12 步想象窗口 | 想象窗口可调（`aim_horizon`），实测 20 步的收益 |
| **分钟级长时程一致性** | 12 步 horizon | 暂时够不到；但暴露了我们"规划视野短"的短板 |

`continuous` 候选集（借鉴的核心）：
1. **朝目标的精确方向**——v1 只有 8 个等分方向，经常错过最优动作
2. **瞄准方向的 ±20°/±10° 邻域**——世界模型对直冲动作常有系统偏置
3. **16 个连续采样**（方向 × 幅度 0.55-1.15×）
4. 惯性 + 减速候选（保留 v1 的）

### 实测：规划策略才是瓶颈（今晚最大的改进）

`eval_planner.py` A/B（16 个 seed，同一批起点）：

| 策略 | 成功率 | 平均步数 | 耗时 |
|---|---|---|---|
| fixed8（v1：8 个固定方向） | 9/16 | 27.1 | 37s |
| **continuous（瞄准 + 邻域 + 16 采样）** | **16/16** | **26.3** | 40s |

**成功率 56% → 100%，步数更少，耗时几乎不变。** 这印证了前面的结论：
世界模型的数据和精度都不是瓶颈，**8 个粗方向的动作候选才是**——
只要把"朝目标"这个精确方向显式放进候选集，MPC 立刻从会晃悠变成不迷路。

想象窗口 20 步 vs 12 步：成功率同为 16/16，步数相同——窗口不是瓶颈，
保持 12（更快）。

### 融合点：参数化动作指令（两者的交汇）

LingBot-World 的动作是**连续控制信号**（action string），MiniMind 的 Tool Call
是**离散工具选择**。两者的交汇是**带参数的工具调用**：

```
MiniMind 式:  [调用工具 world_navigate]
融合后:       [调用工具 world_navigate, direction=西北, magnitude=0.7]
              [调用工具 world_imagine, steps=24]
```

语言模型决定"调哪个工具 + 带什么参数"，世界模型负责把参数变成
"方向 × 幅度 × 步数"的连续控制——这正是 LingBot-World 的 action-conditioned
思想在 agent 层的落地形式。

## 世界模型 v2：混合策略数据（一次没有明显收益的诚实实验）

诊断假设：v1 的动力学只见过**随机策略**轨迹，导致 MPC 规划时"梦里"的动作
分布不匹配。改法：50% 随机 + 50% MPC+PD 分层策略（今天调好的那套），
数据量翻倍，模型结构不变（checkpoint 兼容，不用重训语言模型）。

结果（`eval_world.py` A/B，16 个 seed）：

| | 成功率 | 平均步数 | 感知兼容 |
|---|---|---|---|
| v1（随机数据） | 9/16 | 27.1 | 基准 |
| v2（混合策略数据） | 10/16 | 33.5 | ✓ 潜状态可直接喂给 lm_state |

**结论：提升不显著（+6%），且步数变多**。所以保持 v1 为默认，v2 存档。

### 这一轮真正学到的东西

**数据不是世界模型的瓶颈，规划策略才是。** 动力学在随机数据上已经收敛
很好（loss 0.0016）；MPC 失败的根因是：
1. 想象窗口 12 步的累积误差（超过就失真）
2. 过冲振荡与墙边边缘 case（今天下午已诊断，靠 PD 控制层解决）

也就是说，继续加大数据/换策略分布的收益递减，要提升导航能力得从
**规划算法**入手（更长视野 + 状态记忆，或学一个真正的策略网络）。
这是比"再训一版世界模型"更值得投入的方向。

## 对照 MiniMind：SFT 阶段落地（jingyaogong/minimind）

参考 [MiniMind](https://github.com/jingyaogong/minimind) 的训练流水线，
把我们的语言模型从"预训练式续训"升级为规范的两阶段：

```
Pretrain（已有 lm_final2：2040 万字符工业语料）
    ↓
SFT（train_sft.py + sft_data.jsonl）  ← 本节新增
    ↓
（后续可选）LoRA / DPO / Agentic RL
```

### 对照表：我们借鉴了什么

| MiniMind 做法 | 我们之前 | 现在的做法 |
|---|---|---|
| Pretrain → SFT 两阶段 | 混合语料续训（粗糙） | 规范 SFT：`train_sft.py` |
| **SFT 只对 assistant 算 loss** | 全序列 loss（100% token） | loss mask：**22.9% token** 参与训练，算力省 4 倍 |
| conversations 格式（多轮） | 扁平"问：X 答：Y" | `{"conversations": [{role, content}...]}` |
| Tool Call 混进 SFT | 无 | 68 条工具调用轨迹（感知/导航/检索/计算/想象） |
| cosine lr + warmup | 固定 lr | `cosine_lr()`（warmup 10% → 余弦衰减到 10%） |
| 梯度裁剪 | 无 | `clip_grad_norm_(1.0)` |
| 断点续训存优化器状态 | 只存权重 | checkpoint 含 `opt.state_dict()` |
| 词表 6400 BPE+ByteLevel | char-level 4997 | **待办**（见下方路线） |

### SFT 数据集（799 条）

- 多轮对话（含 system prompt 交代身份，40% 是 2-3 轮追问）
- 知识问答（669 条常识库自动生成）
- **Tool Call 轨迹**（68 条）：user → assistant(tool_calls) → tool(结果) → assistant(总结)

### 关键坑：loss mask 必须在右移之后

TinyGPT 的约定是 `labels[i] = ids[i+1]`（预测下一 token）。
SFT 第一版我让 labels 与 ids **平行**——等于教模型"预测自己"，
loss 假性趋零到 **0.0012**，但生成全是"："。正确做法是
`SFTDataset` 输出 `(ids, learn_flags)`，由 `collate` 做右移后再按
learn_flags 施加 mask。修正后 loss 曲线正常（2.97→1.39→0.72→0.46）。

### 诚实的现状

第一版 SFT（799 条）过拟合到"（认真回答）关于「X」"模板。
扩量到 3503 条（1654 条 tool call）重训后问题解决，并且**模型学会了自主工具选择**：

```
你看到了什么？    → [调用工具 world_perceive]
过去看看        → [调用工具 world_navigate]
23 乘以 7 等于几  → [调用工具 calc]
想象一下往左走   → [调用工具 world_imagine]
长城是什么      → 长城是古代防御工程体系…（知识在参数里，直接答不调工具）
你好           → 我是小WM，一个世界模型加语言模型的迷你 agent。
```

### Agentic 模式：模型自己决定调工具

`reply_agentic()` 实现 MiniMind 的 Agentic 模式——不再靠关键词路由，
而是让 SFT 模型自己输出工具调用，agent 执行后把结果回灌，模型总结成自然语言：

```bash
python agent.py --agentic --dialog lm_sft2.pt "23 乘以 7 等于几"
# → 23 乘以 7 = 161（模型输出 [调用工具 calc] → 计算器执行 → 结果回灌 → 总结）
```

实测端到端：感知（真跑世界模型编码器）→ 结果回灌 → 模型描述画面；
算术（符号计算器）→ 161；知识问答不调工具直接答。

### 远程工具：跨进程调用

`register_http_tool()` 让 agent 把任意 HTTP 端点注册为工具
（同名可覆盖本地实现，`execute_tool` 优先查远程表）：

```python
bot.register_http_tool("kb_query", "http://127.0.0.1:8399/kb")
bot.reply_agentic("柏拉图是谁")   # → 模型调 kb_query → HTTP 到另一个进程 → 总结答案
```

实测：跨进程调用 `api_server.py` 的 `/kb` 端点成功拿回答案，
未命中返回"远程服务没有返回可用结果"（而不是裸 JSON）。

两种模式的分工：
- **路由模式（默认）**：关键词路由 + 潜状态注入，感知精确度更稳（生产用）
- **Agentic 模式**：模型自主决策工具，展示的是"模型会规划调用"的能力

### BPE 分词器（零依赖从零实现，压缩率 1.82）

`bpe_tokenizer.py` 从零实现标准字符级 BPE（pip 的 `tokenizers` 装不上，
不如自己写）。6400 词表（2053 字符 + 4347 merges），训练语料 57.5 万字符。

```
21 字 -> 11 token | 世界模型是一类预测环境动态的神经网络模型
压缩率: 1.82 字符/token（char-level 是 1.00；MiniMind 的 BPE 是 1.5-1.7）
学到的 token: 世界模型 / 语言模型 / 小WM / 目标 / 规划 / 画面 / 64 ...
```

**为什么超过 MiniMind 的 1.5-1.7**：我们的语料是结构化对话，
"世界模型""语言模型""小WM"这类术语反复出现，BPE 能合并成长片段；
通用语料更杂，同样的词表学不到这么长的公共片段。

**意义**：同等上下文长度下 token 数减少 45%——char-level 的效率天花板
（下午诊断出的"记忆天花板"根因）由此解决。代价是**全链路重训**
（词表变了，所有权重都不兼容）：

```bash
python bpe_tokenizer.py --train --vocab-size 6400 --out bpe_6400.json
# 迁移步骤：① TinyGPT 接入 BPE 编码（替换 stoi/itos）
#          ② 用 bpe.encode() 重 tokenize 预训练语料（需重新 download_corpus）
#          ③ 全量重训 pretrain → SFT → 感知模型
#          ④ gen_state_data / train_lm_state 改用 BPE 编码
```
bpe_6400.json 已存档（634KB），作为下一阶段起点。

### 下一步路线（MiniMind 式）

1. **BPE 全链路重训**（上面已写迁移步骤，约 2-3 小时）
2. **扩 SFT 数据到 1 万条**：从当前 3503 条扩到能覆盖真实问答分布
3. **Agentic RL**：环境反馈做 reward，用 GRPO 优化导航策略
   （MiniMind 的 train_agent.py 思路）

## 对话能力：双模型分工（lm_dialog）

单模型干两件事两头都不灵——实测要么感知好但闲聊崩（"你好"答成百科电影条目），
要么闲聊好但感知退化成百科幻觉。最终方案是**分工**：

| 模型 | 职责 | 训练语料 | 实测表现 |
|---|---|---|---|
| `lm_state.pt`（32 维） | 具身感知（潜状态注入） | 26421 条状态-描述对 | 方位/位置判断精确 |
| `lm_dialog.pt`（69.6M→75.5M） | 闲聊/自述/能力介绍 | 385 条手写对话（扩量 8 倍） | 对话模式，零百科幻觉 |
| 常识库 669 条 | 知识问答 | 大小库打通 | 精确命中 |

**四层回答兜底**（`_chat_answer`）：
1. **系统查表**（零幻觉）：身份/能力/礼貌/场景问答直接从对话语料的结构化数据查，
   问法按长度降序匹配（避免"你会什么"劫持"你会什么语言"）
2. **常识检索**：669 条 bigram 索引，查询覆盖率打分
3. **对话模型生成**：闲聊兜底
4. **诚实说不知道**

实测（11 项全部正常，无一百科幻觉）：
```
你好       → 嗨，我在呢。想让我看画面、导航，还是随便聊两句？
你是谁     → 小WM在此。我由两部分组成：一个预测世界怎么变化的世界模型，一个从零训练的语言模型。
你能做什么 → 我能做五件事：一是感知…三是常识检索，六百多条；四是算术…
谢谢你     → 能帮上忙就行。
再见       → 好，去忙吧。世界模型我给你留着。
你会什么语言 → 中文。英文只会蹦几个词，别的就别指望了。
光速是多少 → 光在真空中的速度约 30 万公里每秒…（检索）
```

### 训练踩坑：续训语料必须继承词表

`train_lm_big.py` 原来按本语料重建词表，续训对话语料（800 字词表）时
把 checkpoint 的 4997 词表整个换掉 → embedding/head 形状变化全废
（参数 75.5M→69.6M，loss 2→6 爆炸）。修复：加 `--vocab-from` 从
checkpoint 继承词表（只追加新字符），并让 `train_lm_state.py` 走
"词表增长时复制旧行"的路径。对话语料另加 `--repeat 8` 扩量
（1.5 万字符 → 1200 个训练样本）。

## 世界模型是什么

一句话：**给它当前观测和一个动作，它预测下一刻的世界长什么样。**
预测得足够准，智能体就可以不碰真实环境、在"想象"里试错和规划——这就是世界模型的核心价值。

## 架构：经典三件套的迷你版

```
 观测图像 (1x64x64)                    动作 a_t (2 维加速度)
      |                                     |
      v                                     |
 [Encoder CNN]                              |
      |                                     |
      v                                     v
  z_t (32 维潜状态) --------------> [Dynamics MLP]
                                            |
                                            v
                                  预测的 z_{t+1}
                                      |        |
                            [Decoder CNN]      |
                                      |        |
                                      v        v
                                想象的下一帧   继续迭代 = 开环"梦境"
```

和真实世界模型（World Models / RSSM / Dreamer）同构，只是规模缩小了 5 个数量级：

| 组件 | 这里 | DreamerV3 / Genie 级别 |
|---|---|---|
| 观测 | 64x64 灰度图 | 720p 视频帧 |
| 编码器 | 4 层 CNN | ViT / 3D VAE |
| 动力学 | 128 隐层 MLP | 数亿参数 Transformer |
| 训练数据 | 2.4 万帧随机 rollout | 百万小时视频 |

## 三个实验说明什么

**实验 1 · 一步预测**：真实下一帧 vs 模型想象的下一帧。
想象帧里 agent 的位置、形状都对上了，说明编码器+动力学真的学到了视觉动态。

**实验 2 · 开环想象（rollout）**：完全不碰环境，只用动力学在潜空间迭代 30 步，
把每步想象的潜状态解码成图，从中提取 agent 位置，和真实轨迹对比。
**误差随步数累积**是世界模型的根本难点（每步的小误差会反馈回去放大）。
实测曲线：前 8 步误差 < 0.1（贴合），10 步后开始发散，30 步误差 ~0.8。
真实系统用随机潜状态（RSSM）、扩散强制（Diffusion Forcing）等手段缓解。

**实验 3 · MPC 规划**：每步枚举 8 个方向 + 惯性/减速候选，用世界模型想象 12 步，
选"梦里终点离目标最近"的动作执行。实测 8 个随机 seed 成功率 1/8——
**能通，但不稳**，这正是当前世界模型的真实水平（Genie 3 的演示同样充满穿模和不一致）。
瓶颈在想象保真度：12 步窗口末端预测已明显失真，MPC 会被系统性误导。
提升方向：多步动力学损失、潜状态直接监督、更密的候选动作。

## 踩坑记录（从零训世界模型的 5 个真实陷阱）

这些全是本次搭建中实际撞到并修复的，按撞见顺序排列。每一条都对应代码里的一处注释：

1. **decoder 被 MSE 欺骗，坍缩成"全黑"**
   agent/目标像素只占全图 1%，MSE 损失下"输出全黑"（0.0023）比学画亮点的初期损失还低，
   decoder 直接躺平，想象帧全黑，MPC 彻底失灵。
   → 修复：前景加权 BCE（权重 15，只作用于接近全亮的前景像素）。

2. **联合训练雪崩：encoder 被两个损失拉扯后 dynamics 爆炸**
   dynamics 的梯度流回 encoder，encoder 表征持续漂移，dynamics 输入分布突变，
   误差爆炸后再把 encoder 打爆，dyn loss 从 1e-4 冲到 1.2 亿。
   → 修复：dynamics 输入 `z.detach()`，两个损失解耦；lr 降到 5e-4；梯度裁剪兜底。

3. **保存最后一轮权重 = 保存崩溃权重**
   训练在第 23 轮突然发散，而 checkpoint 存的是最后一轮。
   → 修复：只保存历史最佳权重，不存最后一轮。

4. **世界模型对动作不敏感（action insensitivity）**
   环境每步位移只有 0.03，相对潜状态尺度（std 0.5）信号太弱，
   dynamics 学 identity（忽略动作）就能拿低 loss——8 个候选方向想象终点全挤在一起。
   → 修复：动作效应调大 2.5 倍。真实世界模型的环境动作效应都很大（机器人关节一动几厘米）。

5. **半亮像素被 pos_weight 扭曲**
   给边界（0.25）和圆环目标（0.45）也乘 15 倍权重后，模型被逼着把这些像素预测成 0.83，
   重建劣化 3 倍，argmax 甚至被失真边界抢走。
   → 修复：加权只作用于 y > 0.5 的真前景。另：目标点用空心圆环渲染，
   保证任何帧里 argmax 唯一对应 agent（实心目标盘会在 rollout 中抢走 argmax）。

## 加一个能聊天的模块（常识对话）

**先泼一盆冷水**：世界模型本身没有语言通路——没有词表、没有文本编码器、没有语言输出头，
它的"嘴"长在图像上（解码器输出像素）。"喂常识"喂不进世界模型，它没有消化文字的结构。

正确架构是**两个模块分工**，用"具身查询"打通：

```
[语言模块 chat.py]   常识检索 + 意图路由 + 自然语言生成
      |  ^
      v  |
[具身查询]   你在哪 / 目标在哪 / 想象一下 / 往前走一步
      |  ^
      v  |
[世界模型]   编码器 + 动力学 + 解码器 + MPC
```

这正是具身智能的标准架构：语言模型负责"说"，世界模型负责感知和推演物理世界。

### 对话能力

```bash
python demo_chat.py              # 跑预设对话演示
python demo_chat.py --interactive  # 交互模式
```

四类意图：

| 意图 | 例子 | 实现 |
|---|---|---|
| 常识问答 | 光速是多少 / 柏拉图是谁 | bigram 检索，当前 40+ 条常识 |
| 四则运算 | 23 乘以 7 等于几 | 正则 + 双语运算符 |
| 闲聊 | 你好 / 谢谢 / 再见 | 关键词模板 |
| 世界模型查询 | 你在哪 / 想象一下 / 往前走 | 真跑世界模型，用自然语言汇报 |

### 喂新知识的方法

打开 `knowledge.py`，在对应列表里加一行，不用改任何其他代码：

```python
{"keys": ["量子纠缠", "纠缠"], "answer": "量子纠缠是两个粒子的状态关联，测量一个会瞬间决定另一个，与距离无关。", "tag": "科学"},
```

"keys" 是与用户输入做匹配的关键词，"answer" 是命中后的回答。
库里没有的提问会诚实回答"不知道，但我可以学"，不会编造。

### 两个中文检索的坑（已修）

1. **查询框架词稀释匹配率**："光速是多少"里"是多少"占了 bigram 的一半，
   关键词重叠率被摊薄到阈值以下 → 匹配前先删框架词
2. **英文不能按字符切 bigram**：GPU 切成 "GP""PU" 没有意义 →
   英文/数字串整体作为一个 token

## 升级：从零训练的语言模型（微型 GPT）

检索式对话换成了真·语言模型：**从零手写 GPT，在自建语料上训练，81 万参数，CPU 3 分 44 秒**。

### 架构（GPT-2 的最小化复刻，逐行手写）

```
token embedding + position embedding
-> 3 x [LayerNorm -> 因果多头注意力 -> LayerNorm -> MLP]（残差连接）
-> LayerNorm -> lm head
```

char-level（按 Unicode 字符切分，不用 BPE），词表 802。
注意力、因果 mask、残差、layernorm、dropout 一个不少，只是规模小了五个数量级。

### 训练

```bash
python corpus.py     # 生成语料（370 对问答，约 2 万字符）
python train_lm.py --epochs 500   # CPU 约 4 分钟，loss 6.46 -> 0.017
python lm_chat.py               # 对话演示
python lm_chat.py --interactive  # 交互模式
```

### 三个刻意的架构设计

1. **算术走符号计算器，不走语言模型**
   语言模型是模式补全，不是计算器——让它算 23×7 它只会猜一个看起来合理的数。
   真实 AI 系统也是这样分工的（工具调用），本项目中算术正则命中后直接算。

2. **世界模型查询继续由世界模型回答**
   "你在哪/想象一下"这类问题由世界模型真跑推理后生成自然语言汇报，
   语言模型不掺和——模态分工，各管各的。

3. **幻觉是特性，不是 bug**
   实测："量子纠缠是什么"答成了重力条目（语料里最近似的），
   "你怎么看阿尔法狗"把想象那套话术套了上去。
   语料里有的（370 对问答）采样稳定时能背对，语料没有的就一本正经地编——
   这就是语言模型的本质。`lm_chat.py` 里 temperature=0.7 可调低换取稳定性。

### 能力边界（诚实版）

| 能力 | 状态 |
|---|---|
| 背出学过的问答 | ✓（loss 0.017，但采样仍可能跑偏） |
| 泛化到没学过的问法 | ✗ 会幻觉 |
| 算术 | 走符号模块，正确 |
| 长上下文 | block 95 字符，约 30 个汉字 |
| 常识覆盖面 | 语料里那 370 条，想扩展就往 corpus.py 加 |

要真正常聊天，需要把词表换成 BPE、语料换成 GB 级、参数换成亿级——
那就是另一条显卡赛道了（16G 显存可跑 Qwen2.5-0.5B 级别的推理，
但从零训练仍建议 24G+）。

hf-mirror 限流严重——curl 带浏览器 UA + 请求间隔 5 秒，urllib 连续请求必 429。

### 训练

```bash
# GPU（RX 6800 16G，ROCm）：
H:/ComfyUI_rocm/python_env/python.exe train_lm_big.py \
    --corpus corpus_industrial.txt --scale large --epochs 3 --out lm_industrial.pt
```

实测（2026-10-16）：84.5M 参数（词表因工业语料涨到 12017），
3 epochs 34 分钟，显存峰值 10.3G/17.2G，loss 5.35 → 3.37。

### 关键结论：预训练不等于会聊天

实测输出暴露了真实的差距：

- 问"你好" → 续写新闻体（"我们能够为大家提供，最好是你能让每一个工作人员……"）
- 问"柏拉图是谁" → "柏拉圖是一種數學知識"（流畅但错误的幻觉）
- 问"光速是多少" → 复读问题（"光速是多少的，光速是多少的"）

模型学会了**语言分布**（下一个字大概率是什么），但没学会**对话协议**
（问题后面应该跟答案）。这正是 GPT-3 预训练后还需要 instruction tuning / RLHF 的原因。

### 第二轮：QA 扩充 + 词表过滤 + 降温采样（build_final_corpus.py）

针对上述三个问题的修复：

1. **QA 数据从 2684 对扩到 6 万对**：zhwiki 定义句自动转问答
   （"柏拉图：古希腊哲学家……" → "问：柏拉图是什么？答：古希腊哲学家……"），
   每种问法生成两个变体。QA 占比 5% → 15%
2. **词表过滤**：12017 → 4997（删除出现 <50 次的罕见字符，仅损失 0.34% 文本，
   节省 6M 参数的稀疏 embedding）
3. **降温采样**：temperature 0.7 → 0.5
4. **epochs 3 → 6**

最终语料 `corpus_final.txt`：2040 万字符、4997 词表、79587 训练样本。
训练：75.5M 参数，6 epochs 69 分钟（GPU），loss 4.71 → 2.34，显存峰值 9.2G。

### 第二轮实测：格式对齐成功，知识记忆未完成

- 问"柏拉图是谁" → "柏拉图（）是希腊神话中的一个巨大的神祇"
- 问"阿尔法狗" → "阿尔法狗（，）是一種化學元素，化學符號为，原子序數为62"

进步：**所有问题都会用百科定义句式回答**（对齐的雏形，上一轮还在复读问题）。
差距：**答案内容仍以幻觉为主**——模型学会了"怎么答"，还没记住"答什么"。
6 万对 QA 对 75M char-level 模型来说记忆量偏大（loss 2.34 仍在快速下降，
继续训练会改善）。这是 scaling law 的又一次印证：记知识需要更多 epochs、
更大模型、或更小的知识集合。

### 第三轮：续训 + 语料扩充（train_lm_big.py --resume）

续训功能：按张量形状匹配加载（词表变化时 embedding 重新初始化，其余层继承）。

- **方案① 续训 6 epochs**（2040 万字符，从 lm_final.pt 热启动）：
  loss 2.34 → 1.94，188/188 层继承。**效果实质进步**：
  问"光速是多少"答出"光速是指光在真空中的速度"（核心内容首次沾边），
  问"你好"能自然开头。
- **方案② 语料扩到 5900 万字符**（SkyPile 3 分片 + zhwiki 2 分片 + 12 万对 QA，
  从 lm_final2.pt 热启动训 4 epochs）：loss 3.32 → 2.47。
  **效果回退**——三个原因：
  1. 词表 4997 → 6523，3 个 embedding 层被重新初始化，丢了已学到的关联
  2. QA 占比被稀释：15% → 10%（语料涨了 3 倍但 QA 只涨了 2 倍）
  3. warm start 的 lr（6e-4）对已收敛模型偏大，产生知识干扰

**结论：当前最佳是 lm_final2.pt**（方案①产物）。这也是真实训练中的典型一课：
加数据不总是对的——数据配比、学习率调度、词表稳定性都会影响续训效果。

### 第四轮：修正版重试（词表锁定 + lr 1e-4 + QA 30%）

针对方案②的三个病因修正后重跑：
1. **词表锁定**：用 lm_final2 的 4997 词表过滤新语料（`--vocab-from`），
   embedding 188/188 全继承（只删 0.28% 文本）
2. **lr 降到 1e-4**：避免对已收敛模型的知识干扰
3. **QA 占比 30%**：工业文本降到 3400 万，12 万对 QA 占比反升到 30%

结果（4889 万字符，4 epochs，1h51m，loss 2.35→2.19）：
**追平但未超越 lm_final2**。"光速"答案仍是循环复读，不如 lm_final2 的沾边版本。

### 根因诊断：char-level + 75M 的记忆天花板

连续三轮实验（②回退、修正版追平）指向同一结论：
- 语料从 2040 万加到 4889 万（2.4 倍），loss 在 2.2-2.4 徘徊不动
- 75M char-level 模型记 12 万对 QA 的细节，容量已近极限
- QA 占比 30% 反而压制了工业文本的语言流信号（模型更倾向套百科模板）

真正的下一步（需要换武器，不是调参数）：
1. **换 BPE 词表**：词表 4997→30000，同等参数量下有效序列长度 ×3-5，记忆效率数量级提升（这是所有现代 LLM 的选择）
2. **上更大模型**：16G 显存可训 118M（xlarge 档），但 char-level 的效率瓶颈仍在
3. **精选 QA**：从 12 万对精选 1-2 万高质量对，深度记忆代替广度记忆

## L2 半耦合：世界模型潜状态 → 语言模型（具身对话）

两个模块从"工具调用"（L1）升级为"表征对齐"（L2）：
世界模型编码器实时产出的 32 维潜状态，经投影层注入语言模型的
`[STATE]` token 位置——语言模型回答感知类问题时，是真的"看到"了
世界模型的内部表征。

```
环境观测 → 世界模型编码器 → 32 维潜状态 z
                                  ↓
                              state_proj（Linear 32→640）
                                  ↓
问：你看到了什么？\n[STATE]\n答：……  ← z 的投影加到 [STATE] 位置的 embedding
                                  ↓
                            TinyGPT 生成回答
```

没有 `[STATE]` token 的普通文本样本 mask 全零，state 自动失效——
同一个模型既会具身感知又会普通对话。

### 数据优势（本项目独有）

环境是程序化生成的，每帧观测都有 ground-truth 坐标，
`gen_state_data.py` 自动制造"潜状态→语言描述"配对：
150 个 episode（一半随机策略、一半 MPC）× 60 步 × 3 种问法
= 26421 条样本。答案由环境真值模板生成（八方位 + 距离）。
**真实具身 AI 最稀缺的"视觉状态→语言"配对数据，我们渲染一帧就有。**

### 训练与实测

```bash
python gen_state_data.py --episodes 150        # 生成配对数据（CPU 45 秒）
H:/ComfyUI_rocm/python_env/python.exe train_lm_state.py --epochs 4   # GPU 11 分钟
H:/ComfyUI_rocm/python_env/python.exe demo_state.py                  # 演示
```

从 lm_final2.pt 热启动（词表 4997→4998，embedding 行复制保留知识），
state QA 与 270 万字符普通语料混合防遗忘，loss 1.46→1.07。

实测（agent 在 (0.49,-0.39)，目标在 (0.7,0.63)）：

| 问题 | 回答 | 验证 |
|---|---|---|
| 目标在哪个方向？ | 目标在我的**正南**方向 | 方位角公式手算验证，精确正确 |
| 你看到了什么？ | 灰色圆环是目标点，在**偏下右侧** | target 屏幕坐标 y=0.63 为下、x=0.7 为右，正确 |
| 你离目标多远？ | 直线距离 **0.7** 个单位 | 格式正确；真实值 1.04，**数值记忆有误差**（char-level 的数值精度极限） |
| 往左走三步后再问 | agent 位置描述从"偏下右"变为"偏上右" | 回答随状态变化，证明真在读潜状态 |

### 诚实的边界

- **态势理解对了**：方位、位置关系（上下左右）精确可靠
- **精确数值记不住**：距离这类连续量只能记住大概（char-level 模型的固有极限，
  要精确需把数值单独编码或上回归头）
- **泛化未验证**：训练分布内的状态描述可靠；分布外（如贴墙）未测

### 融合架构实验记录（三个扩展，两个回退）

| 实验 | 做法 | 结果 |
|---|---|---|
| 64 维"预见"（z + 动力学预测） | 后 32 维注入下一刻预测 | loss 更低但感知质量下降（信息密度摊薄），回退 |
| MLP 投影层 | Linear→MLP+GELU 增强融合表达 | 冷启动参数 2 万→23 万，4 epochs 学不动，[STATE] 被注入噪声，感知通道整体失效，回退 Linear |
| 64 维"运动感知"（z + Δz） | 后 32 维注入与上一帧的潜状态差 | 连续失败（MLP 4ep / Linear 6ep），根因：**Δz 信噪比太低**——帧间差尺度远小于 z（~0.1 vs ~3），运动信号被位置信号淹没；冷启动投影层优先学会"忽略 state 也能答对大半" |

运动感知的修复方向（备用，未实施）：Δz 归一化放大到与 z 同尺度 + 10+ epochs +
QA 文本里运动信息占比提高。教训：**加特征不等于加信息，注入通道的有效学习需要
特征尺度匹配**。当前生产配置 = 32 维 z 单帧注入 + Linear 投影 + 分层 MPC/PD。

## 语言即任务：完整 agent 闭环

说完"去目标那儿"，系统执行完整的 **理解 → 规划 → 行动 → 汇报** 闭环：

```
"去目标那儿"  →  任务意图识别
             →  [规划层] 世界模型 MPC：枚举 8 方向+惯性+减速候选，
                每个候选想象 12 步，按"梦里轨迹最近距离"选优
             →  [控制层] PD 逆动力学精密进近：读当前速度，
                用逆动力学算动作，处理固有刹车距离
             →  每 15 步进度汇报（方位 + 剩余距离）
             →  到达 / 超时都有明确交代
```

### 为什么分两层（踩坑三轮的结论）

| 方案 | 成功率 | 失败原因 |
|---|---|---|
| 纯 MPC（12 步想象，终点距离评估） | 1/8 | 想象失真 + 每步重规划抖动 |
| MPC + 全速直冲兜底 | 0/5 | 全速冲过目标，单向贴墙 |
| MPC + 比例减速直冲 | 0/6 | 卡在 0.2 进不了 0.15 的到达圈 |
| **MPC 规划 + PD 控制分层** | **6/8** | 残留失败为墙边边缘 case |

根因：环境有固有刹车距离（阻尼 0.8，带速度冲到近处会冲出 0.7 远），
**想象力擅长中远程选方向，精密进近必须速度感知**——这正是真实机器人
系统 planning + control 分层的道理。MPC 阶段方向选错 3 步无进展即让位控制层。

### 其他完善

- **环境操控**："重置 / 换个新目标" → 开新回合并汇报双方位置
- **边界感知**："墙在哪" → 描述四面边界、撞墙反弹、墙边想象力下降
- **对话记忆**：最近一轮问答入历史，供上下文引用

## 统一系统：MiniWorldAgent（agent.py）

所有模块融合为一个入口类，五层能力一个 `reply()` 路由：

```
MiniWorldAgent
├── 感知层   世界模型（编码器/动力学/解码器）+ 程序化环境
├── 语言层   TinyGPT（32 维潜状态注入生成）+ 常识库检索（兜底）
├── 行动层   MPC 想象规划 + PD 逆动力学精密进近
├── 符号层   四则运算计算器
└── 记忆层   对话历史 + 环境状态
```

路由优先级：算术 → 任务/操控/边界 → 感知（潜状态注入）→ 想象/动作/潜状态 → 常识（检索优先，生成兜底）。

```python
from agent import MiniWorldAgent
bot = MiniWorldAgent()
bot.reply("去目标那儿")      # 行动层：完整导航闭环
bot.reply("你看到了什么？")   # 感知层：32 维潜状态注入
bot.reply("光速是多少？")     # 常识：检索优先
bot.reply("23 乘以 7")       # 符号层：计算器
```

### 检索优先策略（生成+检索的融合结论）

高置信检索命中 → 直接给权威答案；未命中 → 语言模型生成兜底。
早期版本在检索命中时还附生成补充，实测补充全是幻觉噪声
（"德国数学家"式）——**生成的价值在覆盖面，检索的价值在准确度，
命中时不该用噪声稀释权威**。

### 64 维潜状态实验（存档 lm_state64.pt，效果回退）

尝试把潜状态从 32 维（当前 z）扩展到 64 维（z + 动力学一步预测），
让语言模型获得"预见"能力，并新增"你接下来会怎么动"问法训练它用预见通道。
结果（loss 1.07→0.92 更低但）**感知回答质量反而下降**：
- 信息密度摊薄：同样的投影层要编码双倍信息
- next 类数据只占 25%，预见通道没学会（问"接下来怎么动"串台成方位问答）

结论：**不是所有扩展都有效**——32 维 + 分层 MPC 是当前最佳组合。
64 维模型存档备查，`MiniWorldAgent(lm_ckpt="lm_state64.pt")` 可切换对比。

## 内核审核与优化（Claude 视角 code review）

以顶级 agent 框架的标准过了一遍代码，发现并修复 7 项问题：

| # | 问题 | 修复 |
|---|---|---|
| 1 | 世界模型在 CPU、语言模型在 GPU，每次感知跨设备拷贝 | 统一设备：模型本体 `.to(device)`（注意 `load_state_dict(map_location=...)` 不移动模型本体，必须显式 `.to()`） |
| 2 | 导航任务同步阻塞无保护（30-60 秒） | 步数预算 + 90 秒超时 + 持锁执行 |
| 3 | HTTP 多客户端共享 env 单例，状态竞争 | `threading.Lock` 保护任务执行 |
| 4 | history 存了 20 轮但从不进 prompt（死记忆） | 生成时带最近 6 轮上下文 |
| 5 | reply 任一环抛异常整个崩 | 每层 try-catch + 优雅降级（单能力失败不影响其他） |
| 6 | argmax 位置提取无校验（想象失真时静默出错） | `_safe_pos`：有限性 + 世界边界（±1.05）校验，越界候选作废 |
| 7 | 常识大库（580 条）建了却没进检索索引（数据断点） | 索引打通大库+小库：40 → **669 条**，"长城/秦始皇"从查不到变 1.0 命中 |

另外两项打磨：
- 检索打分从 `min(|q|,|e|)` 归一改为**查询覆盖率** `|交集|/|查询|`——短查询（"长城"）不再被歧视
- 魔法数字集中到 `CONFIG`（候选数/想象步数/任务预算/超时/阈值…）

### 优化效果

- 导航任务：**分钟级 → 秒级**（8-14 步的任务 GPU 上亚秒完成，最慢 4 秒）
- 导航成功率：5/6（原 6/8）
- 感知方位判断精确（"偏上右侧"等）
- 常识检索覆盖 669 条
- 错误降级实测：设备 bug 爆发时系统不崩，逐能力独立失败
